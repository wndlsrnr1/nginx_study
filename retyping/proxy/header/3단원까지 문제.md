### 설정 문제

**문제 2-9**  
다음 요구사항에 맞는 nginx 설정을 작성하시오.

- 경로: `/socket`
- 백엔드 서버: `http://backend_server`
- WebSocket 연결 지원
- 기본 헤더 설정 포함 (Host, X-Real-IP)

**답:**
```nginx
location /socket {
    proxy_pass http://backend_server;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
```

---

**문제 2-10**  
다음 설정의 문제점을 찾고 올바르게 수정하시오.

```nginx
location /ws {

}
```

**답:**
**문제점:**
- Upgrade 헤더가 전달되지 않아 WebSocket 연결이 실패함
- HTTP 버전이 1.1로 설정되지 않음
- Connection 헤더가 설정되지 않음

**수정된 설정:**
```nginx
location /ws {
    proxy_pass http://backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
```

### 서술형 문제

**문제 2-11**  
브라우저에서 WebSocket 연결 시 Upgrade 헤더가 어떻게 생성되는지 설명하시오.

**답:**  
브라우저는 JavaScript의 WebSocket API를 사용할 때 (`new WebSocket('ws://...')`), 자동으로 `Upgrade: websocket` 헤더와 `Connection: Upgrade` 헤더를 생성합니다. 개발자가 직접 이 헤더를 설정할 수는 없으며, 브라우저가 보안상의 이유로 자동으로 처리합니다.

---

**문제 2-12**  
nginx에서 `proxy_set_header Connection "upgrade"`를 사용하는 이유를 설명하시오.

**답:**  
nginx는 기본적으로 Connection 헤더를 제거하거나 수정할 수 있습니다. WebSocket 연결을 위해서는 Connection 헤더가 "upgrade"로 설정되어야 하므로, nginx에서 명시적으로 이 값을 설정하여 백엔드로 전달해야 합니다. 이렇게 하지 않으면 백엔드가 WebSocket 핸드셰이크를 수행할 수 없습니다.

### 서술형 문제

**문제 3-12**  
가상 호스팅에서 Host 헤더의 역할을 설명하시오.

**답:**  
가상 호스팅은 하나의 서버에서 여러 도메인을 운영하는 기술입니다. 서버는 요청의 Host 헤더를 확인하여 어떤 도메인으로 요청이 왔는지 판단하고, 해당 도메인에 맞는 설정이나 애플리케이션으로 요청을 전달합니다. 예를 들어, `Host: kotlip.kr` 요청은 애플리케이션 A로, `Host: another.com` 요청은 애플리케이션 B로 라우팅될 수 있습니다.

**문제 3-13**  
`proxy_set_header Host $host;`를 사용할 때와 명시적인 Host 값을 사용할 때의 차이점과 각각의 사용 시나리오를 설명하시오.

**답:**  
**`proxy_set_header Host $host;` 사용 시:**
- 클라이언트가 보낸 Host 헤더 값을 그대로 백엔드로 전달
- 백엔드가 클라이언트의 원본 Host를 필요로 할 때 사용
- 예: 백엔드가 여러 도메인을 처리하고 클라이언트의 도메인을 그대로 사용하는 경우

**명시적 Host 값 사용 시:**
- 백엔드가 기대하는 정확한 Host 값으로 설정
- 백엔드가 특정 Host 값만 허용하거나 가상 호스팅을 사용할 때 필요
- 예: `proxy_set_header Host proxy1.aiserv.ktcloud.com;` (백엔드가 이 값을 기대하는 경우)

**결론:** 백엔드의 설정에 맞춰 적절한 방법을 선택해야 하며, 백엔드가 특정 Host를 기대하는 경우 명시적으로 설정하는 것이 안전합니다.

**문제 3-14**  
프록시 환경에서 Host 헤더를 잘못 설정하면 발생할 수 있는 문제들을 설명하시오.

**답:**  
1. **라우팅 실패**: 백엔드가 Host 헤더를 기반으로 라우팅을 수행하는 경우, 잘못된 Host 값으로 인해 요청이 올바른 애플리케이션으로 전달되지 않을 수 있습니다.

2. **404 에러**: 백엔드가 Host 헤더로 가상 호스팅을 구분하는 경우, 인식하지 못하는 Host 값으로 인해 404 에러가 발생할 수 있습니다.

3. **검증 실패**: 백엔드가 허용된 Host 목록을 검증하는 경우, 허용되지 않은 Host 값으로 인해 요청이 거부될 수 있습니다.

4. **SSL/TLS 인증서 매칭 실패**: 백엔드가 SSL/TLS를 사용하는 경우, Host 헤더와 인증서의 도메인이 일치하지 않으면 인증서 오류가 발생할 수 있습니다.

**문제 종합-1**  
다음 상황을 분석하고 올바른 nginx 설정을 작성하시오.

**상황:**
- 클라이언트: `https://kotlip.kr/api/docs`로 요청
- nginx 프록시 서버
- 백엔드: `https://api_backend` (실제 호스트: `proxy1.aiserv.ktcloud.com`)
- 백엔드는 가상 호스팅을 사용하며 `proxy1.aiserv.ktcloud.com` Host만 허용
- WebSocket 연결도 지원해야 함 (`/api/ws` 경로)

**답:**
```nginx
# 일반 HTTP 요청
location /api {
    proxy_pass https://api_backend;
    proxy_set_header Host proxy1.aiserv.ktcloud.com;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

# WebSocket 연결
location /api/ws {
    proxy_pass https://api_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host proxy1.aiserv.ktcloud.com;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;
}
```

**설명:**
- Host 헤더를 백엔드가 기대하는 값(`proxy1.aiserv.ktcloud.com`)으로 설정
- WebSocket 경로에는 Upgrade와 Connection 헤더 추가
- HTTP 버전 1.1 설정 및 긴 타임아웃 설정
- 클라이언트 정보 전달을 위한 X-Real-IP, X-Forwarded-For 헤더 추가

- [ ] WebSocket을 위해 `proxy_http_version 1.1` 필요
- [ ] 101 Switching Protocols는 WebSocket 핸드셰이크 성공 응답

### 3단원
- [ ] Host 헤더는 HTTP/1.1에서 필수
- [ ] Host 헤더는 가상 호스팅에 사용
- [ ] `$host`는 클라이언트의 Host 헤더 값
- [ ] 백엔드가 기대하는 Host로 명시적 설정 필요
- [ ] 브라우저는 URL에서 Host 헤더 자동 생성
