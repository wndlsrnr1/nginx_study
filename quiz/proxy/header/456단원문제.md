### 서술형 문제

**문제 4-14**  
프록시 환경에서 클라이언트의 실제 IP를 추적하는 것이 왜 중요한지 설명하시오.

**답:**  
클라이언트의 실제 IP를 추적하는 것은 여러 중요한 이유가 있습니다:
1. **로깅**: 실제 사용자 IP를 로그에 기록하여 분석 및 감사 가능
2. **보안**: IP 기반 접근 제어, 침입 차단, DDoS 방어 등 보안 정책 적용
3. **지역 기반 서비스**: IP 기반 지역 판단으로 맞춤형 콘텐츠 제공
4. **문제 해결**: 특정 IP의 문제를 추적하고 디버깅 가능

프록시 없이는 서버가 직접 클라이언트 IP를 알 수 있지만, 프록시를 통과하면 백엔드는 프록시의 IP만 받게 되어 실제 클라이언트 IP를 알 수 없게 됩니다.

---

**문제 4-15**  
`$remote_addr` 변수의 의미와 프록시 환경에서의 동작을 설명하시오.

**답:**  
`$remote_addr`는 nginx 변수로, **직접 연결된 클라이언트의 IP 주소**를 의미합니다. TCP 연결에서 얻은 실제 IP 주소를 저장합니다.

**직접 연결 환경:**
- 클라이언트가 nginx에 직접 연결하면 `$remote_addr`에 클라이언트의 실제 IP가 저장됨

**프록시 환경:**
- nginx는 클라이언트와 직접 연결되어 있으므로 `$remote_addr`에 클라이언트 IP가 저장됨
- 하지만 nginx가 백엔드로 요청을 전달할 때, 백엔드는 nginx와 직접 연결되어 있으므로 백엔드의 `$remote_addr`에는 nginx의 IP가 저장됨
- 따라서 백엔드가 클라이언트의 실제 IP를 알려면 X-Real-IP 헤더로 전달해야 함

---

**문제 4-16**  
X-Real-IP 헤더의 보안 고려사항과 사용 시 주의점을 설명하시오.

**답:**  
X-Real-IP 헤더는 비표준 헤더이며, 다음과 같은 보안 고려사항이 있습니다:

1. **헤더 조작 가능성**: 클라이언트가 직접 X-Real-IP 헤더를 설정할 수 있어 신뢰할 수 없는 소스가 됨
2. **신뢰할 수 있는 프록시**: 반드시 신뢰할 수 있는 프록시(내부 네트워크의 nginx 등)에서만 이 헤더를 설정해야 함
3. **추가 검증**: 보안이 중요한 경우 IP 화이트리스트나 추가 검증 로직 필요
4. **다중 프록시 환경**: 첫 번째 프록시에서만 실제 IP를 설정하고, 이후 프록시는 값을 그대로 전달해야 함
5. **X-Forwarded-For와 함께 사용**: 더 정확한 IP 추적을 위해 X-Forwarded-For와 함께 사용하는 것이 권장됨

### 서술형 문제

**문제 5-14**  
`$proxy_add_x_forwarded_for` 변수의 동작 방식을 상세히 설명하시오.

**답:**  
`$proxy_add_x_forwarded_for`는 nginx의 특수 변수로, 다음을 수행합니다:

1. **기존 헤더 확인**: 요청에 `X-Forwarded-For` 헤더가 있는지 확인
2. **헤더가 없는 경우**: 현재 클라이언트의 IP(`$remote_addr`)만 반환
3. **헤더가 있는 경우**: 기존 값에 콤마와 공백을 추가한 후, 현재 클라이언트의 IP를 추가하여 반환

**예시:**
- 클라이언트 IP가 `192.168.1.100`이고 헤더가 없으면: `"192.168.1.100"`
- 클라이언트 IP가 `192.168.1.100`이고 기존 헤더가 `"203.0.113.5"`이면: `"203.0.113.5, 192.168.1.100"`

이렇게 하면 다중 프록시 환경에서 IP 체인을 유지하면서 각 프록시의 IP를 추가할 수 있습니다.

**문제 5-15**  
X-Real-IP와 X-Forwarded-For의 차이점과 각각의 사용 시나리오를 설명하시오.

**답:**  
**X-Real-IP:**
- 단일 IP 주소만 전달
- 프록시 하나만 있을 때 사용하기 적합
- 설정이 간단: `proxy_set_header X-Real-IP $remote_addr;`
- 단일 IP만 필요하므로 파싱이 간단

**X-Forwarded-For:**
- IP 체인(여러 IP를 콤마로 구분)을 전달
- 다중 프록시 환경에서 사용하기 적합
- 프록시 경로 전체를 추적 가능
- 설정 시 `$proxy_add_x_forwarded_for` 사용 (기존 값 보존)
- 첫 번째 IP가 실제 클라이언트 IP

**사용 시나리오:**
- **단일 프록시**: X-Real-IP만으로 충분하지만, X-Forwarded-For도 함께 사용 가능
- **다중 프록시**: 반드시 X-Forwarded-For 사용 (X-Real-IP는 첫 번째 프록시에서만 설정)
- **권장**: 두 헤더를 모두 사용하여 유연성 확보

**문제 5-16**  
백엔드에서 X-Forwarded-For 헤더의 IP 체인을 파싱하는 방법과 주의사항을 설명하시오.

**답:**  
**파싱 방법:**
1. X-Forwarded-For 헤더 값을 읽음
2. 콤마로 분리하여 배열로 변환
3. 첫 번째(가장 왼쪽) IP를 실제 클라이언트 IP로 사용

**Python 예시:**
```python
def get_client_ip(request):
    x_forwarded_for = request.headers.get('X-Forwarded-For', '')
    if x_forwarded_for:
        client_ip = x_forwarded_for.split(',')[0].strip()
    else:
        client_ip = request.remote_addr
    return client_ip
```

**주의사항:**
1. **첫 번째 IP가 실제 클라이언트**: IP 체인에서 가장 왼쪽의 IP가 원본 클라이언트 IP
2. **신뢰할 수 있는 프록시**: 클라이언트가 직접 헤더를 조작할 수 있으므로 신뢰할 수 있는 프록시에서만 사용
3. **공백 제거**: IP 사이에 공백이 있을 수 있으므로 `strip()` 사용
4. **빈 값 처리**: 헤더가 없거나 비어있을 경우 `$remote_addr`를 대체값으로 사용
5. **보안**: 보안이 중요한 경우 IP 화이트리스트나 추가 검증 로직 필요

**문제 6-14**  
SSL Termination 환경에서 X-Forwarded-Proto 헤더가 왜 필요한지 설명하시오.

**답:**  
SSL Termination 환경에서는 프록시 서버에서 SSL/TLS를 종료하고, 백엔드 서버와는 일반 HTTP로 통신합니다. 이로 인해 다음과 같은 문제가 발생합니다:

1. **프로토콜 정보 손실**: 백엔드는 HTTP로 요청을 받지만, 실제로는 클라이언트가 HTTPS로 요청했는지 알 수 없음
2. **리다이렉트 URL 생성**: 백엔드가 리다이렉트 URL을 생성할 때 올바른 프로토콜(HTTPS)을 사용해야 함
3. **보안 검증**: 백엔드가 HTTPS만 허용하는 경우, 원본 프로토콜을 확인해야 함
4. **쿠키 설정**: Secure 쿠키는 HTTPS에서만 전송되므로, 원본 프로토콜을 확인해야 올바르게 설정 가능

X-Forwarded-Proto 헤더를 사용하면 프록시가 원본 프로토콜 정보를 백엔드로 전달할 수 있어, 백엔드가 올바르게 동작할 수 있습니다.

**문제 6-15**  
`$scheme` 변수의 의미와 동작 방식을 설명하시오.

**답:**  
`$scheme`은 nginx 변수로, **요청이 들어온 프로토콜**을 의미합니다.

**값:**
- `$scheme = "http"`: HTTP 요청
- `$scheme = "https"`: HTTPS 요청

**동작 방식:**
1. 클라이언트가 HTTPS로 nginx에 연결하면 `$scheme = "https"`
2. 클라이언트가 HTTP로 nginx에 연결하면 `$scheme = "http"`
3. nginx는 TCP 레벨에서 프로토콜을 감지하여 변수에 저장

**사용 예시:**
```nginx
proxy_set_header X-Forwarded-Proto $scheme;
```
- HTTPS 요청: `X-Forwarded-Proto: https`
- HTTP 요청: `X-Forwarded-Proto: http`

이렇게 하면 백엔드가 원본 프로토콜을 알 수 있습니다.

**문제 6-16**  
백엔드에서 X-Forwarded-Proto 헤더를 활용하는 방법과 활용 사례를 설명하시오.

**답:**  
**활용 방법:**
1. 헤더에서 프로토콜 정보 읽기
2. 기본값 처리 (헤더가 없으면 HTTP로 가정)
3. 프로토콜에 따른 동작 수행

**활용 사례:**

**1. 리다이렉트 URL 생성:**
```python
def get_redirect_url(path):
    proto = request.headers.get('X-Forwarded-Proto', 'http')
    host = request.headers.get('Host', 'localhost')
    return f"{proto}://{host}{path}"
```
- HTTPS로 접속했으면 HTTPS URL로 리다이렉트
- HTTP로 접속했으면 HTTP URL로 리다이렉트

**2. 보안 검증:**
```python
proto = request.headers.get('X-Forwarded-Proto', 'http')
if proto != 'https':
    return "HTTPS required", 403
```
- HTTPS만 허용하는 엔드포인트에서 검증

**3. Secure 쿠키 설정:**
```python
proto = request.headers.get('X-Forwarded-Proto', 'http')
secure = (proto == 'https')
response.set_cookie('session', value, secure=secure)
```
- HTTPS인 경우에만 Secure 쿠키 설정

**4. 로깅:**
```python
proto = request.headers.get('X-Forwarded-Proto', 'http')
logger.info(f"{proto.upper()} request from {client_ip}")
```
- 프로토콜 정보를 포함한 로깅

**주의사항:**
- 클라이언트가 헤더를 조작할 수 있으므로 신뢰할 수 있는 프록시에서만 사용
- 헤더가 없을 경우 기본값(HTTP) 처리 필요

**문제 종합-3**  
다음 복합 시나리오에 맞는 완전한 nginx 설정을 작성하시오.

**시나리오:**
- 도메인: `example.com`
- HTTP(80)와 HTTPS(443) 모두 처리
- 일반 HTTP 요청: `/api` 경로
- WebSocket 요청: `/api/ws` 경로
- 백엔드 서버: `http://backend_server`
- 백엔드가 기대하는 Host: `api.example.internal`
- 클라이언트 IP, 프로토콜 정보 전달 필요
- 다중 프록시 환경 지원

**답:**
```nginx
# HTTP와 HTTPS 모두 처리
server {
    listen 80;
    listen 443 ssl;
    server_name example.com;
    
    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;
    
    # 일반 HTTP 요청
    location /api {
        proxy_pass http://backend_server;
        
        # Host 헤더
        proxy_set_header Host api.example.internal;
        
        # 클라이언트 IP 정보
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        
        # 프로토콜 정보
        proxy_set_header X-Forwarded-Proto $scheme;
    }
    
    # WebSocket 요청
    location /api/ws {
        proxy_pass http://backend_server;
        
        # WebSocket을 위한 HTTP 버전
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        
        # Host 헤더
        proxy_set_header Host api.example.internal;
        
        # 클라이언트 IP 정보
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        
        # 프로토콜 정보
        proxy_set_header X-Forwarded-Proto $scheme;
        
        # WebSocket 타임아웃 (연결 유지)
        proxy_read_timeout 3600s;
    }
}
```

**설명:**
- HTTP와 HTTPS 모두 처리하는 서버 블록
- 일반 HTTP 요청과 WebSocket 요청을 분리하여 처리
- WebSocket 경로에는 Upgrade와 Connection 헤더 추가
- 모든 경로에 클라이언트 IP, 프로토콜 정보 전달
- Host 헤더를 백엔드가 기대하는 값으로 명시적 설정
- 다중 프록시 환경을 고려한 X-Forwarded-For 사용

## 암기 체크리스트

### 4단원 (X-Real-IP)
- [ ] X-Real-IP는 비표준 HTTP 헤더로 클라이언트의 실제 IP를 전달
- [ ] `$remote_addr`는 직접 연결된 클라이언트의 IP 주소
- [ ] 프록시 환경에서 백엔드는 프록시의 IP만 받음
- [ ] `proxy_set_header X-Real-IP $remote_addr;`로 설정
- [ ] 브라우저는 IP 정보를 HTTP 헤더에 포함하지 않음
- [ ] 다중 프록시 환경에서는 첫 번째 프록시에서만 설정
- [ ] X-Forwarded-For와 함께 사용하는 것이 권장됨

### 5단원 (X-Forwarded-For)
- [ ] X-Forwarded-For는 IP 체인을 기록하는 비표준 헤더
- [ ] 다중 프록시 환경에서 클라이언트 IP 추적에 사용
- [ ] `$proxy_add_x_forwarded_for`는 기존 값을 유지하며 IP 추가
- [ ] 첫 번째 IP가 실제 클라이언트 IP
- [ ] `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`로 설정
- [ ] IP들은 콤마로 구분됨
- [ ] 브라우저는 X-Forwarded-For 헤더를 생성하지 않음
- [ ] X-Real-IP와 함께 사용하여 유연성 확보

### 6단원 (X-Forwarded-Proto)
- [ ] X-Forwarded-Proto는 원본 프로토콜(HTTP/HTTPS)을 전달
- [ ] SSL Termination 환경에서 필수
- [ ] `$scheme`은 요청이 들어온 프로토콜 (http 또는 https)
- [ ] `proxy_set_header X-Forwarded-Proto $scheme;`로 설정
- [ ] SSL Termination에서 백엔드는 HTTP로 요청을 받음
- [ ] 브라우저는 프로토콜 정보를 HTTP 헤더에 포함하지 않음
- [ ] 리다이렉트 URL 생성 시 올바른 프로토콜 사용 가능
- [ ] 다중 프록시 환경에서는 첫 번째 프록시에서만 설정

### 공통 사항
- [ ] 모든 헤더는 비표준이므로 신뢰할 수 있는 프록시에서만 사용
- [ ] 클라이언트가 헤더를 조작할 수 있으므로 보안 고려 필요
- [ ] 다중 프록시 환경에서는 첫 번째 프록시에서 원본 정보 설정
- [ ] 실제 환경에서는 백엔드 설정에 맞춰 적절한 값 사용
